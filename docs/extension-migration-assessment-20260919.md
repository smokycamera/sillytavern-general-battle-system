# 战阵：酒馆助手与原生扩展比较（2026-09-19）

> 本文保留迁移前评估。原生扩展现已实现；当前结果见 [README](../README.md) 和 [验收记录](native-extension-validation.md)。

结论：建议把原生前端扩展作为后续主形态，分阶段解除酒馆助手依赖；当前新版脚本继续作为可用交付。迁移有明确的维护和集成收益，但不是现有功能可用的必要条件。先对齐用户最新成品与源码，再开展迁移。此次完成评估与交付基线替换，没有实施扩展迁移。

## 比较对象

酒馆助手本身就是酒馆前端扩展，它进一步提供脚本运行层。战阵当前作为这个运行层里的脚本，通过隐藏 iframe 启动，再向主窗口挂载面板 iframe。该机制可在助手的[官方仓库说明](https://github.com/N0VI028/JS-Slash-Runner)中核实。

本报告中的原生扩展指带 `manifest.json` 的 SillyTavern UI extension。官方提供上下文、事件、设置、聊天元数据和生成拦截器等接口，建议优先使用 `SillyTavern.getContext()`，避免依赖内部模块路径。[官方扩展文档](https://docs.sillytavern.app/for-contributors/writing-extensions/)

战阵不需要增加 Node 服务端插件：当前引擎是本地 JavaScript。TauriTavern 的项目说明明确支持前端扩展，并说明其 Rust 后端不支持上游 Node-only 后端插件；其扩展管理支持原生 Git 安装和更新。这个定位适合保持 SillyTavern 与 TauriTavern 两端兼容。这里核对的是上游当前说明，未读取用户已安装应用的准确版本。[TauriTavern 官方说明](https://github.com/Darkatse/TauriTavern/blob/main/README.md)

## 对当前新版的具体发现

以下以用户 JSON 提取出的 `panel/dist/controller.js` 和 `index.html` 为主要证据；`panel/src` 仅用于对照架构，不假定它与新版完全一致。

1. **已具备可迁移边界。** 存在统一 `createAdapter()` 和 `NarrativeController`，战斗引擎、规则、库存、正文协议及视图可逐步复用，迁移无需重写伤害或经验公式。
2. **仍有助手硬依赖。** `inTavern = !!th?.getVariables`；没有助手时，即使存在原生上下文，`injectPrompts` 仍会提前返回。`load/save`、`getEnvelope`、发送也依赖助手 API。简单增加 manifest 并不能独立运行。
3. **已经部分使用原生能力。** 订阅优先尝试酒馆核心事件，提示投影调用 `setExtensionPrompt`，常驻控制器也已有 dispose。迁移收益是统一剩余路径、减少兼容分支，不能将这些现有能力当成全新收益。
4. **存在重复代码与启动工作。** 当前 JSON 为 2,471,657 bytes（约 2.36 MiB）；提取面板为 1,398,415 bytes，控制器约 981,583 bytes。两份都包含 `SmallBattle`、`MassBattle`、伤害计算、适配器和存档编解码等模块。这证明存在拆分机会，不代表可以直接省去某个固定比例。源码打包方式、压缩和加载策略也会影响大小；不能将新版比旧版大归因于清理失败。
5. **轮询并未完全退出。** 控制器每 1.5 秒检查身份；适配器还有按需启动的消息轮询路径。原生版可在事件支持已验证时减少重复检查，对缺能力宿主保留降级。
6. **保存接口需要实质调整。** 当前 `save()` 同步返回回执，内部写助手变量并同步写压缩 localStorage 镜像，对异步调用通过立即读回确认内存值。原生持久化应等待宿主保存完成，并在切聊天、快速连续操作和失败时保持正确事务。不能只把函数名替换成 `saveMetadata()`。
7. **分组聊天不是迁移后自动获得。** 现实现的 namespace 在 `groupId` 存在时直接返回空。原生版若要支持群聊，需要定义角色/群组/聊天/分支身份和独立验收。

## 方案比较

下表的收益判断来自上述代码结构；它们是设计评估，没有实测性能提升比例。

| 维度 | 保留酒馆助手脚本 | 原生前端扩展 | 对战阵的判断 |
| --- | --- | --- | --- |
| 安装与更新 | 导入 JSON，依赖助手，适合随卡分享 | 独立扩展目录与版本，接入宿主扩展管理 | 长期维护收益高；需维护可安装的发布仓库 |
| 启动与生命周期 | 隐藏脚本 iframe、面板 iframe、pagehide 清理 | 独立入口，按宿主能力接入就绪与启停 | 可减少一层运行依赖；仍须实现幂等注册及卸载 |
| 状态和存档 | 助手变量加压缩本地镜像 | 聊天状态与设置分开，直接适配宿主持久化 | 保存回执和容量管理更清晰；不会自动获得无限容量 |
| 事件与提示注入 | 已使用部分原生接口，同时保留助手桥和轮询 | 统一宿主事件和生成边界 | 减少重复订阅与调试分支；保留重生成、停止等防重复语义 |
| UI 和启动体积 | 单文件方便传递；多份模块随脚本加载 | 常驻入口小型化，打开面板后再加载视图 | 有直接优化空间；初期可保留 iframe 的样式隔离 |
| 引擎性能与 token | 本地 JavaScript 结算，模型负责叙述 | 仍是本地 JavaScript 与同一模型输入 | 不自动加速、不自动省 token；需要各自的性能和提示策略优化 |
| 兼容维护 | 适配助手和宿主的组合 | 适配 SillyTavern/TauriTavern 版本 | 少一个必需依赖；仍有宿主 API 演进成本 |
| 开发发布 | 单个 JSON 简单，但易与源码版本脱节 | 可建立源代码、版本、构建、发行对应关系 | 原生形态有帮助，版本管理问题仍需工程流程解决 |

SillyTavern 的扩展管理支持第三方 Git URL 安装及更新管理；不是所有版本都应假定存在同样的新生命周期 hook。迁移时需要按能力探测并声明兼容范围。[官方扩展安装说明](https://docs.sillytavern.app/extensions/)

## 优化优先级

**第一优先：单一状态源与可靠保存。** 保留一个常驻 controller 管理事务，面板只提交意图和读取视图。设置进入扩展设置，当前聊天状态进入专用命名空间。把保存回执改为能够等待真实持久化的接口，事务按聊天串行，失败保持可恢复状态；提交前后校验聊天身份。不要把所有历史战报塞进每次都保存的全局设置。

**第二优先：保护清理后的数据。** 当前加载器会在宿主值与本地镜像之间按 revision 选择较新者；因此空对象本身不能表达“用户已清理”。迁移应以用户确认的当前聊天数据为源，逐聊天一次性导入并登记版本。需要保留清理标记或数据代次，防止旧镜像、旧备份重新成为权威数据。备份用于恢复，不自动合并回当前状态。没有源数据的聊天保持为空。

**第三优先：拆分加载与重复包。** 把最小正文协议处理和宿主适配留在常驻入口，战场 UI、重型报告展示等按需加载。引擎模块在可共享的同一执行环境中复用；若暂留面板 iframe，应显式传递操作与快照，不能以为浏览器资源缓存会让不同 iframe 自动共用同一个 JS 模块实例。先量测启动耗时、关闭面板内存、打开延迟，再决定是否改成主页面挂载或 Shadow DOM。

**第四优先：事件驱动与完整清理。** 原生事件能力验证通过后，合并重复事件桥和身份轮询；关闭视图时卸载视图订阅，停用扩展时注销监听、计时器和提示注入。生成开始、结束、停止、编辑、删楼层、swipe、切聊天仍需保留幂等处理；单独收到“生成结束”不能证明一定存在完整有效的助手消息。

**第五优先：大存档与长战报。** 避免每次 UI 操作都对全部历史 JSON 序列化、压缩、读回。可研究按变更提交、历史报告延迟读取、本地 IndexedDB 缓存与导出。实际需要跨设备/随聊天迁移的权威数据必须通过宿主可携带的存储或显式导出解决；浏览器缓存不应成为唯一档案。若实测长战斗自动结算阻塞 UI，再评估 Web Worker，同时保持随机种子和结果一致。

**第六优先：提示词按阶段输出。** 利用已有的手动范围、参战/本场相关、观测边界与增量战报，减少世界书、常驻事实和用户发送摘要的重复。保持用户手工选择及完整事实语义，避免靠静默截断省 token。以同一聊天事实下的最终请求测 token；JSON 体积、JavaScript 压缩和原生化本身与模型输入长度不是同一指标。

前四项适合作为原生迁移主线；后三类性能、存储和提示优化也可以在脚本形态下先做，无需等到迁移完成。

## 推荐实施路线与工作量判断

| 阶段 | 可审查交付 | 主要工作量 |
| --- | --- | --- |
| 0：源码对齐 | 用户新版变更进入可构建源码，成品行为可复核 | 当前前置条件，不能靠旧源码重新构建绕过 |
| 1：独立原生入口 | manifest、入口、设置与按钮；保留当前面板 | 较小；若仍调用助手，只能称为过渡版 |
| 2：解除助手依赖 | 原生消息/事件/提示/存档适配，异步保存事务 | 中到较大，是迁移主体 |
| 3：数据迁移与互斥 | 清理后存档导入、版本标记、旧脚本与新扩展互斥 | 中等；保留回滚且防止双重监听、双重提交 |
| 4：加载与存储优化 | 模块拆分、缓存、性能测量 | 可拆开实施，以数据决定继续范围 |
| 5：宿主验收 | SillyTavern 与实际 TauriTavern 版本通过关键流程 | 必需；模拟环境不能代替真实宿主 |

最终验收至少覆盖：关闭面板继续处理；切聊天/群聊身份（若实现）；普通生成、继续、重生成、swipe、停止、编辑与删除；保存失败后重试；旧脚本和新扩展不会重复执行；清理后的空数据不被旧镜像补回；同一战斗种子与操作序列的数值和战果一致。

不建议在同一阶段重写战斗规则和全部 UI。先让新版功能独立于助手、正确保存并兼容真实宿主，再做可量测的性能改造。既有世界书和用户自定义提示词需保持可控，避免迁移时重复注入规则。
