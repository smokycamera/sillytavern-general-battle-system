# 副 API 失败排查与修复（2026-10-01）

现象：开战前读取上下文的副 API 几乎每次都报错，无法开战。按当前源码重建真实请求，把多组模型回答送入与开战相同的校验与本地生成流程复现。失败不只来自提示词，有三类原因。

## 原因

1. **提示词**
   - 没有完整的回答结构。
   - 要求“只返回 selections”，同时又要求 battlefield。
   - 只在“选择小战时”要求地图。但 siege、escort、intercept 和室内会把会战改为小战，模型选了会战就不给地图，随后必然失败。
   - 校验强制的规则没有写明：ID 格式、名称字符、段落引用格式、各类型可用的状态、部队与地点各自可用的关系、场景与地点类型的搭配。
2. **校验过严**：一个回答里有几十个条目，任一条目出现格式偏差（引用带方括号、名称含“、”、northeast、敌方 north_of 河等），整次请求就失败。
3. **本地生成缺陷**：即使回答完全符合提示词，以下场景也会失败。
   - 塔楼锚点落在道路上时不另找位置。
   - occupies/inside 指向建筑、塔楼、门这类实心格时，没有部署位置。
   - 小地标装不下整方部队。
   - 同时写了整方关系和单个单位关系时，单位被要求同时站在两处。
   - 同一方多条关系的部署区没有交集。
   - 未写方位的河流穿过城墙。
   - 地点“靠近并位于某处北侧”时，按地图北缘放置，离该处过远。

## 修改

- **提示词**
  - 给出完整回答结构与格式示例。
  - 有地图规则时始终要求 battlefield。
  - 逐项写明上述硬规则，以及“分兵用单位短 ID 逐个写”。
  - commanders 只写 preferences。
- **回答修正**（`panel/src/llm-battlefield-repair.ts`、`llm-context.ts`）：映射无歧义的偏差在严格校验前修正，每项都写入开战摘要。
  - 引用中的方括号去掉，未发送的段落忽略。
  - 非法 ID 重新编号，关系跟随旧 ID 或名称。
  - 名称中的分隔符改为“·”。
  - 方位拼写规范化。
  - 不适用的状态省略。
  - 部队方位改为该地一侧的部署。
  - 第二条河或第二座城合并到主河、主城。
  - 场景装不下的类型改用相近类型。
  - 改写后的关系只作为推断。
  - 引擎的严格校验不变，手动或 MCP 提交的 JSON 仍逐项报错。
- **本地生成**（`engine/src/small`）
  - 塔楼避开道路。
  - 实心地点从门口部署，平台从顶部部署。
  - 占据范围按兵力延伸到附近地面。
  - 单位自己的关系优先于整方关系。
  - 部署区无交集时取并集。
  - 未定方位的河流沿城外开放一侧布置，必要时换轴。
  - “靠近”的地点布置在对象旁，有方位时偏向该侧。
  - 浅滩可保留任务目标。

## 验证

| 项目 | 修改前 | 修改后 |
| --- | --- | --- |
| 33 种回答格式偏差 | 1 通过 | 30 通过，余下 3 项为故意保留的矛盾事实 |
| 10 类常见正文场景 × 20 个种子，每方 4 个单位 | 59/200；渡口桥头、客栈/关隘/书房/前沿壕线被占据、营门 7 类全部失败 | 200/200 |
| 600 个按新提示词规则随机生成的场景意图 | 328/600（55%） | 552/600（92%），余下为相互矛盾的随机方位 |

修改前最常见的失败是“某方 occupies 某地点”。普通地标只有 1 格，每方超过 2 个单位就无法部署；建筑等实心地点则一个单位也放不下。正文中“敌军占据/据守某处”很常见，因此几乎每次都失败。

全量测试：除仓库已记录的 7 项基线失败外全部通过，TypeScript 检查通过。新增生成器测试在修改前的代码上均失败。实际成功率仍取决于用户的服务商与模型。较长的提示词与地图设计可能需要一分钟以上，单次请求截止时间由 45 秒改为 120 秒。
