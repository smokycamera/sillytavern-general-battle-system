# 副 API 两步准备与攻守部署修复（2026-10-02）

现象：正文是正常的围城（攻方在城外、守方守城），开战后双方都被部署到城内。

## 原因

按当前源码把同一段围城正文的10种常见回答送入开战流程（引擎生成与部署全部真实执行，只替换模型回答）：4种双方同在城内，1种攻方在城内而守方在城外，1种直接报错。原因有三层：

1. **关系措辞被当作几何。** 模型常把“我军接近城池”写成 `ally approaches_from 城市` 或 `ally near 城市`。部署区取“距该地点3格内的所有格”，而城区内的格子距城市本身为0，于是整座城都算攻方的接近区。
2. **关系部署区替换了场景默认区。** 攻城地图本来给攻方城外接近带、守方城内防区；只要一方写了任何地点关系，这一方就改用关系区，不再与攻守区取交集。
3. **部署评分把近战单位拉向任务目标。** 攻城目标在城中心，所以近战攻方被排到城区深处。

另有两处同类问题：城外野战或巷战带城市时，默认部署仍按“敌方上三排、我方下三排”，不看城市实际位置；城与河同侧或河流未写方位时，河道可能穿过城区，把守军和城墙隔开。

对 flash 模型而言，问题不在“没理解正文”，而在协议要求它用 ID、关系动词、段落引用和多份规则同时表达空间，任何一处用词偏差都会被本地忠实执行。

## 修改一：本地按攻守身份部署（对所有来源生效）

副 API、MCP 和手动 JSON 都经过同一套部署规则（`engine/src/small/force-deployment.ts`）：

- 攻城开局时攻方只在城外；城墙只朝一面时，还只在城墙正面一侧，城后和两侧不算接近区。攻方对城市本身写的关系（接近、靠近、驻守）只表示进攻方向，改用城外接近带。
- 守方对城市或城门的关系限于城内，并保留城头，默认仍有约四成守军上墙。守方指向城外地点（如桥头、林地）时视为出城迎击，照常部署在该处。
- 只有单个单位明确“潜入/占据”城内某个具体地点时，才可以在城内开局。
- 城外野战时双方都在背景城镇之外，巷战时双方都在街区内；未写位置的一方在自己那侧的城外或城内开局。
- 每次调整都以短句列在地图上方“查看布局依据”的折叠列表里，例如“攻方改在城外接近青石城”；战场顶部的摘要只显示指挥、任务和战场概况。

## 修改二：副 API 改为两步

开启“由 LLM 设计地图”时依次发送两次请求。关闭时仍只请求1次，地图由本地随机生成。

| 步骤 | 模型要做的事 | 输出 |
| --- | --- | --- |
| 第1步 开战决策 | 双方指挥能力与风格、战斗规模、环境、昼夜、任务、攻城方、VIP、**战场类型**、**战场大小** | 与原来相同的 `selections` 选项键，以及可选的 `commanders` 偏好 |
| 第2步 布置战场 | 按第1步确定的场景，在九宫格上写城市、水系、地点、双方开局方位、单独行动的单位和任务地点 | 一个扁平 JSON，没有 ID、引用或关系动词 |

战场类型的选项直接说明了双方与城墙的位置，例如“城墙攻防：攻方在城外攻城，守方在城内或城头”。第2步的任务文字再写明本场谁攻谁守、地图约多大，列出参战单位，并附一个按攻守方向生成的示例。会战不需要地图，第1步选会战时不发第2步。

两步使用同一条 system 消息和同一条正文消息，只有最后的任务消息不同。DeepSeek、Gemini 等支持前缀缓存的服务商可以复用第1步的正文部分；是否命中和计费方式取决于服务商。

### 九宫格回答格式

```json
{"archetype":"gate_front","cover":"balanced",
 "city":{"at":"N","name":"青石城","wall":3,"breaches":0,"gates":[{"name":"南门","state":"closed"}]},
 "water":{"type":"river","at":"E","bridges":[{"name":"石桥","at":"NE","state":"intact"}]},
 "places":[{"type":"hill","name":"东坡","at":"SE","height":2}],
 "ally":{"at":["S","SW"]},"enemy":{"post":"wall"},
 "units":[{"unit":"u3","at":"NE"}],"objective":"府衙"}
```

- 方位为 `NW N NE / W C E / SW S SE`，上北下南，是地图的绝对方向。解析器也接受“北方、城南、东北角、north_east、左上”等写法。
- 攻城时守方只需写 `post`：`wall` 城头为主，`inside` 不上墙，`outside` 出城列阵并写城外方位。攻方即使写了岗位也会被忽略。
- `bridges` 写出全部桥梁，`[]` 表示没有桥；`gates` 省略时为一座城门，门位放在面向攻方的城墙上。野战中写空的 `gates` 表示没有城墙的城镇。
- 护城河，以及与城市同侧的河流，沿城外开阔一侧布置，不穿过城区。
- 野战任务为攻城、又写了城市时，改用城墙攻防地图。
- 室内地图只保留房间、掩体、要点、废墟和工事，地点类型按此换成相近类型或省略。城门、桥和任务地点优先占用12项场景实体的上限，剩余名额按书写顺序留给其他地点。
- 本地把回答编译成原有的 `battlefield` 计划，并用与手动 JSON 相同的严格校验检查。九宫格回答没有“明确事实”，因此方位和高度都不会因为生成时的微调而整体失败；桥门数量和状态仍按回答生成。

### 失败与重试

- 报错会标明失败的步骤，例如“上下文读取失败（布置地图）”。
- 再次开战时，错误只带回出错的那一步：本地地图生成失败的原因放进第2步的任务文字，不会干扰第1步的决策。
- 每步请求的截止时间为120秒，取消或准备内容变化后，迟到的回答不会生效。

### 兼容

MCP 与手动 JSON 仍使用原来的 `scene-intent` 协议，校验同样严格。新增可选的 `deployments: [{subject, at, post?}]`，用于按九宫格写开局位置。同一部队若已用关系写了部署，以关系为准。

`panel/src/llm-battlefield-repair.ts` 只服务于旧的单次请求回答，已经删除，其中的方位、名称和类型别名移入了新的解析器。已保存的旧战场快照和旧开战摘要照常读取。

## 界面文字与数值显示

- 设置页“上下文与开战配置”、准备页提示和读取状态都改为一句话说明，只保留用户需要知道的内容：作用、额外请求次数、正文会发送给所填服务。
- 精力、疲劳、恢复量、经验等带小数的数值最多显示一位小数；经过四舍五入或截断的数值前加“≈”，精确值照常显示。进度类数值（当前精力、疲劳、本级经验）向下取，距离升级的差值向上取，避免看起来已经达到门槛。不足0.1的经验奖励保留两位。
- 回合变化里的疲劳与资源变化先去掉浮点误差再显示，不再出现“疲劳+0.7699999999999999”。存档中的数值精度不变。

## 顺带修复的原有问题

- 围攻院落时，目标建筑若标为已毁，院门会被清零耐久却仍是“关闭”状态，触发“结构数据损坏”。现在院门随之记为已毁。
- 城外野战加城墙时，地图中心的参考格可能被城墙压住（“目标必须是合法可通行格”）。现在改到最近的城外空地。
- 窄地图上的攻城默认攻方带可能贴着城墙。空间足够时，现在与城墙至少隔一格。
- 攻城和巷战中，城外的重要建筑附近没有现成房屋时会直接失败。现在像野战一样在空地上建造。塔楼在城内找不到可改建的房屋时，改放到城外最近的空地。

## 验证

均为本地验证，没有调用真实收费模型。

| 项目 | 结果 |
| --- | --- |
| 旧协议10种围城回答（MCP/手动 JSON 路径） | 修改前：4种双方同在城内，1种攻方在城内。修改后：9种攻方全部在城外、守方在城内或城头。剩下1种是正文“北门”与“城在北”的明确矛盾，仍按旧协议报错 |
| 两步流程18个固定场景（攻城10、其他场景8） | 全部生成；攻城场景攻方0人在城内或墙上，守方全部在城内或城头（出城列阵一例按要求在城外） |
| 随机回答压力测试，4个种子共3200次 | 覆盖6种场景、4—24张卡，方位、岗位、水系、城门、桥和单独部署均随机。全部生成成功，违规0次：攻方在城内或墙上、守方无故在城外、野战背景城内有人、敌对单位开局相邻，均未出现 |
| 新增与改写的测试 | 新增 `engine/tests/force-deployment.test.ts`、`panel/src/llm-layout.test.ts`；按两步流程改写 `llm-map-design`、`llm-context`、`battle-planning-v2` 和 `main.integration` 中的副 API 用例 |
| 全量测试 | 1748项中1741项通过，失败的7项正是 `check-layered-test-baseline` 记录的已知基线，没有新增失败；`test:extension` 231项、`test:jev-relay` 通过；TypeScript 检查通过 |
| 浏览器预览 | 本地构建候选包，替换宿主模型后端后完整点击开战：两次请求的 system 与正文完全相同；攻方8人均在城外，守方8人均在城内，其中6人在城头；任务绑定到回答中的“府衙”；控制台没有错误 |

`verify:compatibility` 中的两个冻结场景脚本在未改动的 HEAD 上同样失败，差异是战报的胜负行和 haste 字段，与本次改动无关。

flash 模型的实际成功率取决于服务商和模型版本，本轮不提供未经实测的数字。复现脚本与结果保存在本地 `artifacts/siege-deploy-repro/`（不入库）。

## 代码入口

- 两步请求与共享前缀：`panel/src/llm-context.ts`，传输函数为 `panel/src/jev-connection.ts` 的 `openAiJsonRequest`。
- 第2步提示词、宽松解析与编译：`panel/src/llm-layout.ts`。
- VIP 选择：`panel/src/llm-map-design.ts`。
- 攻守身份、九宫格部署与旧关系裁剪：`engine/src/small/force-deployment.ts`，在 `scene-compiler.ts` 和 `layered-generator.ts` 中调用。
- 计划协议中的 `deployments`：`engine/src/small/battlefield-plan.ts`。
