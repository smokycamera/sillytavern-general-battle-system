# 重进聊天后自动批准不生效（2026-10-12）

基线：`1af8b45`（test）。只改原生扩展的存档会话判断（`runtime/src/native-store.ts`、`runtime/src/battle-service.ts`），不改规则版本、存档格式和世界书。旧脚本模式按聊天身份字符串比对，不受这个问题影响，没有改。

## 现象

开着“自动批准所有受支持的战外事件”，离开聊天再进来后，第一条带 `<tb>` 的回复不会自动入账，停在“待处理”，也没有写原因。之后的回复又能自动入账，所以看起来像是“把自动批准关掉再打开才生效”。

关掉再打开其实不是修好它的那一步：这时（在第一条回复被扫描之前）开关是点不动的，面板只提示“聊天已刷新，请点“重新读取存档”或重新扫描”；第一条回复被扫描时插件已经顺带重读了存档，之后不管开关有没有动过，下一条回复都正常。

## 原因

插件用“聊天身份 + 会话代次”判断手里的存档是不是当前聊天的：酒馆换了聊天附加数据对象（chat metadata）或消息数组对象，代次就加一，插件认为档案已经过期，暂停一切写入，直到重新读档。

酒馆（包括 TauriTavern 的 `updateChatMetadata` 和一些扩展）会在不发“聊天已切换”事件的情况下，把同一个聊天的附加数据换成一个合并后的新对象。9 月的 #22 已经确认用户环境里会这样，当时的处理是“扫描回复前发现过期就重读，但这条回复只给人工确认”。进入聊天时恰好最容易发生这种替换：

1. **读档完成后才换**：档案停在“过期”状态。发送消息时插件抓不到生成起点（自动批准要靠它确认回复是在当前档案上生成的），这次生成也不会注入战阵上下文；回复扫描时重读存档，结果只给人工确认。
2. **读档途中就换**：插件判定“载入时聊天已切换”，进入出错状态，效果同上。

## 修改

- **同一个聊天、存档没变就接着用**（`NativeStore.adoptContext`）：代次变了但聊天身份相同、没有未确认的保存、也没有正在进行的读写，而且换进来的附加数据里仍是插件手里这一版存档（文档、代次、版本、操作号、内容散列都一致），就直接接上新的会话代次，不重读、不作废。换进来的对象里存档不一致（比如被整份重置）时照旧重读，回复只给人工确认。
- **读档途中被换**：从文件读到的存档仍然有效，只要还是同一个聊天就采用，不再报“载入时聊天已切换”。读档期间又发起了新的读档（换聊天再换回来）时，只采用最后一次的结果。
- 写入前检查、生成起点、上下文注入、扫描回复、面板的“能否操作”判断统一走这个检查。扫描只在真的换了聊天时取消；同一聊天的对象被替换时保留这次生成的绑定，入账前仍按原规则核对档案版本和单位版本，期间档案被改过照旧判为过期。
- 开着自动批准、回复却只能人工确认时，记录里写明原因：“自动批准只处理档案就绪后生成并直接收到的回复；这条不符合（例如刚进聊天时档案还在读取，或回复被编辑、切换过），请核对后确认”。以后再遇到可以直接看到是哪种情况。

## 验证

- **浏览器复现与对照**：分别用改动前（`runtime/` 未改动的工作区，含同日尚未提交的冲锋修复，只涉及引擎）和改动后的构建，在会保存聊天消息的模拟宿主里按酒馆的真实事件顺序操作：打开自动批准 → 生成一条回复 → 离开聊天 → 重新进入 → 宿主把附加数据换成合并后的新对象 → 再生成。脚本与构建在 `artifacts/auto-approve/`（本地，不入库）。

  | 情形 | 改动前 | 改动后 |
  | --- | --- | --- |
  | 读档途中被替换 | 面板只显示“载入时聊天已切换”和“重新读取存档”按钮；第一条回复停在待处理 | 状态栏“准备就绪”；第一条回复自动入账 |
  | 读档完成后被替换 | 状态栏“聊天已刷新，请点“重新读取存档”或重新扫描”；点自动批准开关只弹同样的提示、开关不变；第一条回复停在待处理，没有原因 | 状态栏“准备就绪”，显示“自动批准已启用”；第一条回复自动入账 |
  | 上一行之后关掉再打开开关 | 能点了，下一条回复自动入账（第一条回复扫描时已经重读过存档） | 不需要 |
  | 没有生成起点的回复（直接收到的消息） | 待处理，没有原因 | 待处理，记录里显示上面的原因 |

  控制台没有错误。
- **新增测试**（`runtime/tests/battle-service.test.ts`）：重进聊天后宿主在读档途中、读档完成后换入附加数据，第一条回复都自动入账（两项，改动前的代码上都失败）；换入的对象不含当前存档时照旧重读、回复只给人工确认。原有的“附加信息对象被替换后可恢复扫描”改为替换后仍可直接写入，没有生成起点的回复带上原因。`panel/src/scan-readiness.integration.test.ts` 的“扫描按钮恢复失效会话”改用不含当前存档的对象模拟失效，仍覆盖扫描恢复、读取失败显示原因与重试。
