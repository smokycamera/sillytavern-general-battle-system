# LLM 指挥：逐单位控制、阵营视野与计划记忆

产品版本：2.8.0；功能分支：`codex/llm-enemy-command`，按用户要求更新至 `test`。

## 使用与兼容

在设置中启用普通 LLM 读取上下文，配置副 API，再勾选 **LLM 指挥**。该项默认关闭；旧配置不会自动开启。原来的“由 LLM 选择战场规模”控件隐藏，旧的规模选择记录不再驱动开战规模；界面继续按卡数选择小战或会战。

指挥设置只提供 **思考／非思考** 两档，默认显示“思考”，请求中不附加思考控制参数。选择“非思考”后可展开“高级兼容设置”，编辑仅用于战斗指挥的 JSON 参数；默认是 DeepSeek 的 `{"thinking":{"type":"disabled"}}`，也可改为供应商支持的格式或 `{}`。合法 JSON 自动保存，格式无效时保留最后的有效设置；附加参数不能覆盖模型、消息或工具等基础字段。切回思考后不发送这些附加参数，再切回非思考保留用户修改。2.8.2 起，人设生成保持 API 默认行为；原有开战、地图和扫描请求也不受该选项影响。

副 API 继续使用 OpenAI 兼容的 `/chat/completions` 与 function calling。工具对话在激活内保留服务端返回的 `reasoning_content` 和 `extra_content`（包括 Gemini 的工具思考签名），激活结束后丢弃，存档白名单也不会保存这些内容。DeepSeek Flash 已经真实调用；Gemini 等其他供应商本次只验证兼容请求、参数透传和签名回传，没有其密钥进行真实端到端测试。

选项用于新战斗。开战前，在原有决策和可选地图生成后，为每个受控阵营增加一次指挥官简报生成。两方战斗增加一次，三方小战分别为敌军和第三方增加一次。正在进行、没有简报的旧战斗继续使用内置 AI。玩家本方的手动、单位托管和全自动入口继续沿用原来的行为。

小战只指挥当前激活单位。2.8.3 起，`commander_act` 可在 `then` 中按顺序写出本次激活的后续行动，程序逐步匹配新候选执行；某步不再合法、出现新的可见单位、本单位受伤或状态改变时停止，以最新观察和停止原因再次询问。会战一次请求用 `commander_orders` 为全部编队下令，冲突或无效的编队带错误和刷新后的候选再问，再按原有阶段统一结算。魅惑、混乱和强制跳过行动沿用引擎处理。会战加速阶段的补充行动保留原有引擎逻辑。三方会战仍受现有引擎限制，三方指挥用于小战。

所有动作由既有引擎执行。战斗规则版本不升级；本功能不重建旧地图，不改写历史数值规则。2.8.1 起，人设生成和逐单位决策的当前请求最多尝试3次，间隔1秒，单次超时120秒；网络、超时和无效回答均可重试，只重发当前决定，不重放已经选过的行动。耗尽后丢弃本次单位激活或本阵营本轮军令的候选结果，该阵营本场后续使用内置 AI；其他阵营的指挥不受影响。暂停、切聊天、改连接和准备条件变化后，不应用旧请求返回的结果。

## 信息范围与工具

模型每次直接收到己方视角的简表、当前指定单位的合法候选、简报、总计划、简短记事和最后目击摘要。2.8.3 起，小战首条消息还包含行动单位完整状态 `self` 和紧凑地图 `map`：`rows` 每格一个字符（`?` 未探索，结构覆盖地形，`legend` 给出含义），`features` 列出非零高度、门、平台、通道、覆盖物和梯道；地图只在激活内探索变化时重发。移动候选压缩为 `moves`，列含义见 `moveColumns`。可见单位简表包含编号、名字、坐标或阵位、等级、人数或生命、状态、高度，以及当前行动者的个人 LOS。所有阵营在各自请求中均将自己称为 `friendly`，另外两个阵营分别用 `opponent-1`、`opponent-2` 区分。

| 工具 | 返回或执行的内容 |
| --- | --- |
| `commander_map` | 已探索地格的编号、x/y、地形、地面高度、结构遮挡高度、掩体、门状态、平台、楼梯或坡道连接和最后观察回合。当前可见地格额外返回当前单位对地面和平台的几何 LOS；会战返回公开阵位拓扑。 |
| `commander_unit` | 己方详细状态、装备、资源、可用技能与道具、冷却；可见对手的名字、等级、位置、人数或生命和个人 LOS；离开视野的对手只返回旧目击记录。未知编号返回未知。 |
| `commander_plan` | 只写变化部分：`plan` 替换总计划（最多 **600 字**，省略不变），`addNotes` 新增、`removeNotes` 按序号删除记事；记事最多 12 条，超出删去最早的条目，每条最多 300 字，程序端验证上限。 |
| `commander_act` | 小战按候选编号提交一个动作，可附 `then` 后续步骤。支持移动、主副武器、冲锋、已准备技能、道具、固守、警戒、压制、装填、升降、开关门、上下平台、破障和结束激活。 |
| `commander_orders` | 会战为本次列出的每个编队各选一个候选编号。 |

己方共享视野、当前单位个人观察、几何 LOS 和动作是否合法是不同信息。工具分别表示前几项；武器射程、贴身限制、间接攻击、状态、行动额度和消耗继续由引擎决定。门、楼台、墙体和高度使用实际地图结构。不能通过查询未探索坐标或未知单位获得其当前状态。

运行时请求不携带完整战斗快照、玩家军令、其他指挥官的简报或计划、原始剧情正文、隐藏单位当前状态或未探索地图。开局设定步骤单独读取所选正文，按照用户确认的提示词生成己方人设与剧情情报。剧情情报属于模型生成摘要，可能误述数字；实际坐标、人数、生命和合法操作每次由程序从当前观察提供。运行时控制只接受本次候选编号。

2.8.2 的生成请求明确发送 `perspective:{self,playerFaction,controlledUnits}`，受控单位仅含本阵营真实编号和姓名。按用户确认并修正的两句提示词，正文中的第一人称归于剧情实际叙述者，受控阵营用于选择指挥官、经历、习惯和任务，区分玩家身份与生成角色。

## 上下文与存档

每个指挥官状态绑定本场战斗种子和受控阵营。敌军、第三方分别使用独立控制器、请求对话、600 字计划、记事、已探索地图和最后目击记忆。另一个阵营的计划不会进入本阵营工具结果。底层接口接受 `ally`、`enemy`、`neutral`，为以后增加友军指挥预留接入方式；当前界面没有启用友军 LLM 控制。

同一小战单位激活期间保留工具对话，动作后追加当前观察，避免每次移动后丢失刚查询的资料。激活结束后清理这段对话，下一单位只接收简报、计划、记事与结构化记忆。已探索地格和对手目击记录按当时数据冻结，重新看见才更新。

这些状态保存在本场 `encounterContext.llmCommanders` 中，随战斗快照一起恢复。继续沿用原有保存策略：战中推进使用会话内快照，持久化节点保存与之对应的指挥状态。没有增加每次模型请求都写宿主磁盘的操作。

战斗界面在 AI 策略下方、投降右侧提供“llm笔记”，以只读弹窗分别显示各阵营的人设、任务、总计划、笔记和开局情报；查看不会调用模型或保存事实，指挥请求进行中也可打开。读取和保存时执行白名单清理，不保留原始模型回复、请求消息、思考或工具对话；开战设计已固化到战场后不再在上下文中重复保存。收兵后清除活动指挥上下文。

## DeepSeek 官方 Flash 实测

日期：2026-10-21。调用官方 `/models` 确认模型 ID 为 `deepseek-flash`，请求发送到官方 `api.deepseek.com`。密钥从用户提供的本地文件读取，不写入源码、存档或报告。

最初的默认思考模式对照，单次请求中位耗时 3.712 秒，四次小战激活耗时 17.667–40.526 秒。保留激活内工具对话后，重复查询减少，但一次谨慎型激活仍耗时 63.118 秒，说明只保留上下文并不能解决推理耗时。

下列非思考实测采用官方支持的 `thinking: {type: "disabled"}`，对应界面“非思考”的默认参数；发布版本由玩家选择，不再按官方 Flash 的地址自动强制关闭思考。依据：[官方 Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/) 与 [Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/)。

下列为2.8.0期间的历史样本，当时人设生成也使用非思考参数。2.8.2 起开关只影响战斗指挥，不再沿用该样本人设生成请求的模式。

最终两种人设、四次小战激活、一轮会战的样本共 29 次请求，请求耗时中位数 **1.790 秒**，95 分位 **3.059 秒**。具体结果：

| 用例 | 人设生成 | 单位1激活 | 单位2激活 | 实际行为 |
| --- | ---: | ---: | ---: | --- |
| 谨慎型岑岳 | 3.820秒 | 11.700秒 | 6.415秒 | 两队分段推进至52、51格，保持邻接，本轮没有抢入45格据点。174字计划强调协同与防范未知威胁。 |
| 激进型程烈 | 2.956秒 | 14.098秒 | 8.376秒 | 第一队进入45格据点并射击，第二队推进后射击。149字计划强调抢点和主动压迫。 |
| 两队会战 | 2.739秒 | 合计下令与结算13.721秒 | — | 两队分别获得合法射击军令，统一结算到下一回合。 |

两种人设均沿用明确的指挥官姓名和性格；计划与行为体现出差异。未知伏兵“紫獾”没有进入其开局简报或后续指挥请求。上述为有限、固定场景样本，能够说明本次表现，不能据此推断长期人设遵循率或稳定延迟。

仅比较保留激活内对话的四次小战单位激活，排除人设生成和会战：

| 指标 | 思考 | 非思考 |
| --- | ---: | ---: |
| 四次激活的 HTTP 请求数 | 17 | 20 |
| 平均每次激活耗时 | 28.637秒 | 10.147秒 |
| 平均每次激活输入 token | 25,934 | 32,874 |
| 平均每次激活输出 token（含思考） | 3,986 | 611 |
| 其中思考 token | 3,387 | 0 |
| 平均每次激活总 token | 29,920 | 33,485 |

四次合计分别为：思考输入103,735、输出15,944（其中思考13,547）、总计119,679，缓存命中输入85,504；非思考输入131,496、输出2,444、总计133,940，缓存命中输入97,664。思考 token 已包含在输出中，不能再次相加。非思考在本样本中平均耗时降低约65%，但因为多次工具查询、输入结构也有细微增加，总 token 反而约高12%；这不是严格同请求数、同输入的基准，不能得出非思考必定更便宜的结论。缓存输入、未缓存输入与输出的计费也不同，未据此推算费用。

输入累计量包含每次工具请求再次发送的提示词、观察、候选、计划及本激活对话，并非这些 token 全部同时留在存档或跨整场战斗累积。总计划最多600字，激活间只保留必要结构化记忆；参战单位越多、模型查询越频繁，总请求数和累计输入就越多。

例如非思考样本中谨慎型第一队的六次请求，输入依次为2,389、2,986、4,874、6,258、7,408、8,367，合计32,282，其中缓存命中24,192。最初请求并非三万输入；地图／单位工具结果及多次动作后的观察追加到激活内对话，每次继续时再次发送，形成累计量。另一组第一队六次请求累计54,689，单次最高12,382。这里的统计单位是“一个单位完成本次激活”，不能标成整场或一个全局回合。结构化工具结果和重复上下文仍有可压缩空间，本次未新增付费模型调用。

另做一组明确任务的定向操作实测，使用同样的正式提示词和工具，实际经过引擎执行：

| 操作 | 单位激活耗时 | 引擎结果 |
| --- | ---: | --- |
| 使用急救剂 | 2.433秒 | 生命10→34，剂数2→1。 |
| 开门 | 4.340秒 | 16格门由关闭变为打开，消耗主行动。 |
| 上楼台 | 3.537秒 | 15格地面→14格平台，高度0→2。 |
| 下楼台 | 8.494秒 | 14格平台→15格地面，高度2→0。 |
| 关门 | 5.462秒 | 16格门由打开变为关闭。 |

该场目标由己方远处观察哨看见，但当前工程官被墙挡住。工具返回 `visible: true`、`losFromActor.canSee: false`、`geometric: false`，与引擎相符。地图查询也返回了高2地格、梯道连接、平台和掩体。

定向操作样本用于验证模型能选择、工具能执行这些操作；任务由测试逐次明确指定，不据此推断模型会自行规划出同样的操作顺序。真实宿主的转发路径、网络负载和战斗规模会影响耗时。

本地原始响应统计与结果保留在忽略目录 `artifacts/llm-command-flash/`，不作为安装包内容。

- 14 个相关测试文件、115 项测试通过，覆盖原有普通 LLM 开战、自动战斗、会战、反应击杀后轮转、传输和新增指挥功能。
