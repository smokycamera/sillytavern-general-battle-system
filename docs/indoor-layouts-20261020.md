# 室内布局改进与其他地图审阅（2.6.9）

## 问题与实现

2.6.8 的室内入口只有 `residence`、`great_hall`、`fortress`。`scene-layouts.ts` 总是先画纵向走廊和两侧小室，堡垒主要改分段距离，大厅再拆掉中段隔墙。副 API 的 `room` 只落成一格地标，不能真正表达房间。室外路网的变化在室内重建时被清掉，增加同一骨架上的家具数量不能解决这个问题。

现在先建立房间区域，再从共享边界建立连接，最后放置家具：

| 空间骨架 | 实际组织 |
| --- | --- |
| suite 穿堂连室 | 连续房间，门位错开，部分布局带单侧通道 |
| hall 主厅侧室 | 大主厅与小侧室；正文指定北或南主厅时保留该方向的大空间 |
| ring 环形回廊 | 两侧房间链在两端连通，形成回路；两翼独立分段 |
| cross 交叉通道 | 纵横通道连接四周房间 |
| wings 双翼联通 | 两组独立分段的房间，通过联络门连接 |
| aisles 货架通道 | 前后房间、中央高货架、架端空间和横向通道 |
| cells 走廊小室 | 偏置走廊连接两侧长度不同的小室 |
| broken 破损连室 | 递归分房、错位开口、局部宽缺口和瓦砾 |

用途与骨架分开：住宅、客栈酒馆、殿堂寺院、仓库、工坊、办公设施、牢房、废弃建筑。用途选择合适的本地候选、房间名称和家具布置。没有副 API 时也使用新生成器。

没有镜像、双方等距、等量房间或公平阵位约束。门位、房间分段、主厅两端隔间及家具使用地图随机源；不消耗战斗骰子。统计时合并镜像只用于去重，不参与地图生成。

命名房间绑定完整实际区域，按房间整体位置而非最近一格选择；明确的东西侧房间会在需要时分出侧室。主厅类名称优先绑定该方向的较大房间。室内明确以“间、房、室、厅、殿”结尾却被模型写成 `position` 的地点，按房间兼容。低掩体仍采用已有掩体机制，高货架采用已有硬障碍机制，不增加新的战斗加成；家具的 `height` 不再误写成地面抬高。

新室内地图记录生成版本7。战场快照和战斗规则版本不变；加载旧战斗读取已有地形，不重新生成。其他五类场景仍走原生成器。

## 副 API 提示词与备份

用户确认的改动仅有两处：室内第2步增加 `interior:{use,pattern}` 说明；室内示例增加 `"interior":{"use":"residence","pattern":"suite"}`。用户随后要求删除“正文未确定的项省略，由程序变化”，实际模板没有该句。其余场景的提示词未改。

修改前的完整源码与一份渲染文本保留于 [prompt-backups](prompt-backups/README.md)。旧模型不返回新字段时仍能生成，错误枚举逐字段回退，不丢掉有效房间、用途和部署。

## 可复现的空间抽样

基线提交：`10bd4b9d12a8c213c9a73646d506fd5cd12bd89b`（2.6.8）。每个条件使用相同60个种子，直接调用真实 `generatedLayeredField`。总计678次生成，包含三种尺寸、旧风格入口、本地随机入口和房间语义对照，无生成失败。

“墙门骨架”保留完好墙、建筑、塔、门的位置，去掉低家具差异，并合并水平/垂直镜像。它衡量结构分布，不等于房间连通图种类，也不是乐趣或平衡评分。

## 真实 DeepSeek 测试

只请求官方 `https://api.deepseek.com` 的 `deepseek-v4-flash`。官方已将旧名路由至后续 Flash，用户已明确同意；实际响应模型名均为 `deepseek-flash`。没有改用 Pro 或其他模型。[官方模型说明](https://api-docs.deepseek.com/zh-cn/)

密钥从用户指定文件在运行时读取，不写入源码、报告或响应记录。测试复用产品 `LlmContextController` 的真实两步准备、JSON解析、本地生成、部署、开战及快照恢复。正文为专门编写的中文场景，不是用户聊天数据。报告保存回答与实际地图，按预先定义的事实核对，不使用模型自评分。

室内12段正文各重复2次，覆盖八种明确骨架与四种需要模型推断的场所。两轮各24场都首次完成两步请求并成功开战。第一轮事实核对21/24，修正整体房间方位匹配后，第二轮为22/24；第二轮剩余两项分别为值守间被模型写成要点、较大的北正殿被绑定到小侧室。修正兼容与主厅匹配后：

- 对第二轮保存的24份真实回答重新解析、生成和开战，24/24通过当前定义的事实核对。这部分是回答重放，不是新增 API 请求。
- 对牢房、神庙两个场景重新真实请求，共4场，4/4首次成功且事实核对通过。
- 实际检查建筑用途、明确骨架、命名房间的面积与方位、北正殿的主要空间地位，以及部署、开战和恢复。有限样本不代表所有正文都能完整建模。

需要真实请求时显式执行：

```sh
npx vite-node scripts/audit-deepseek-maps.ts --key-file=用户密钥文件 --group=indoor --repeats=2
```

测试脚本固定模型与官方目标，不自动换模型。使用 `--replay=已有报告` 可以离线重放，不读取密钥、不产生 API 请求。

## 其他地图：仅审阅，未改生成

五类其他场景，各两段正文、每段重复两次，共20场真实 Flash 测试。20/20首次成功生成、部署、开战和恢复，完成的事实核对20/20。双重城墙按外门与对应内门合计两处门核对。检查覆盖场景类型、指定水桥、城墙形制、攻守内外身份等；不把通过这些事实当成完整复刻所有建筑细节。

另每类60个种子，与提取出的2.6.8引擎逐张对照，300/300实际几何一致。

| 场景，60张 | 完整几何去重 | 去掉低家具并合并镜像后的结构去重 | 审阅结论 |
| --- | ---: | ---: | --- |
| 野外 | 60 | 31 | 基本地形有变化；水系和通路的语义表达仍较粗 |
| 城墙攻防 | 60 | 53 | 墙形、水桥和攻守身份能落地；后续可细审城门接近空间和多段城区 |
| 城内巷战 | 60 | 54 | 街区骨架有差异；副 API 的重要建筑通常仍是封闭地块，不是可进入室内 |
| 围攻单个院落 | 57 | 1 | 优先级最高：固定矩形院墙与正面入口，主要变化来自家具和地标 |
| 堑壕 | 60 | 58 | 局部折线、交通壕有变化；宏观仍主要是两条相对前沿壕，再添加纵深段 |

这些统计跨场景不直接比较好坏：堑壕结构也保留 `fortification`，野外保留水系，自然硬障碍与城市墙段的含义不同。建议下一轮首先处理建筑围攻，其次处理堑壕的整体组织；这轮未应用这些建议。

## 外部参考及取舍

- [Edgar-DotNet](https://github.com/OndrejNepozitek/Edgar-DotNet)：用房间连接图配合房间轮廓和可用门位。采用其“先结构、再房间与门”的思路；没有引入 .NET 运行时，也没有直接移植整个库。
- [Ludomotion：The Theory of the Place](https://www.ludomotion.com/blogs/the-place/)：开发者说明主要地点、接近路径及次入口如何形成多条轨迹。用于区分回路、双翼和主厅侧室，保留用途上的连贯性。
- [graph-dungeon-generator](https://github.com/halftheopposite/graph-dungeon-generator)：TypeScript 项目将生成、连接与绘制分开。其作者说明当前不支持环路，适合参考分层结构，不能作为回廊生成的直接替代。
- [ROT.js 地图模块](https://github.com/ondras/rot.js/blob/master/src/map/index.ts)：提供多个独立生成器。参考不同空间问题分开构造的做法，没有新增依赖。
- [WaveFunctionCollapse](https://github.com/mxgmn/WaveFunctionCollapse)：主要约束局部邻接，作者也提醒简单瓦片集不会自动形成有趣的整体结构。本次没有用局部拼块代替整体连通设计。
- [English Heritage：Lilleshall Abbey](https://www.english-heritage.org.uk/visit/places/lilleshall-abbey/History/description/)：真实遗址中，中央回廊连接教堂、会议厅、食堂，并有贯通侧翼的通道。参考空间关系，不按建筑尺寸照搬。
- [大都会博物馆：明轩](https://www.metmuseum.org/learn/educators/lesson-plans/the-chinese-garden-court)：资料展示房间、庭院和多条游线的组织。参考多入口与路径选择；实际室内战斗仍使用已有室内地面与结构规则。

## 验证与边界

- 室内专项检查：八种骨架的三种尺寸、开门后的全地面连通，实际命名房间与家具重叠，独立门状态，主要房间与侧室，重复种子与存档恢复。
- 原有场景/城市和布局解析专项通过；扩展测试285项与 JEV relay 5项通过；TypeScript 检查通过。
- 旧冻结兼容脚本仍有既有差异：`verify-recovered-scenarios.ts` 期望5个预备能力，现有引擎生成6个；`verify-native-compatibility.ts` 的旧控制器丢掉 activation/haste/intel 等后来增加的快照字段。未修改这些断言，也未扩大已知失败允许列表。
- 原生构建与安装包一致性核验通过，50个打包文件版本均为2.6.9；原生浏览器 smoke 通过。八张真实回答生成的地图通过战斗界面渲染检查，布局对照的八种选择均更新正常，320px宽度不溢出。
- 上述两个旧冻结兼容差异均已用修改前 `10bd4b9` 的引擎重新运行脚本复现；不属于本次地图变更引入的问题。

本次不增加多层楼板、窗户攀入、钥匙锁或新的家具战斗数值；这些需要独立机制，不能只凭地点名称模拟成已支持。
