# 高楼层自动批准不生效、面板卡在“未保存”（2026-10-19）

基线：`a5dc9b1`（test，已含 `c272720` 高楼层读档优化）。改动原生扩展的存档会话判断、保存核验、自动批准扫描和战报投递（`runtime/src/native-store.ts`、`runtime/src/battle-service.ts`、`host/src/sillytavern.ts`、`host/src/messages.ts`、`host/src/message-identity.ts`、`host/src/contracts.ts`），以及面板的回执判断和状态栏显示（`extension/src/panel-runtime.ts`、`panel/src/panel-runtime.ts`、`panel/src/main.ts`）。不改规则版本、存档格式和世界书。

## 现象

- 聊天楼层很高时，开着自动批准，带 `<tb>` 的回复不自动入账，停在“待处理”，原因写着“自动批准只处理档案就绪后生成并直接收到的回复……”。
- 回复后点开面板，状态栏有几秒显示“上一次保存还没确认成功，请先处理上方提示”（红字，带“重新读取存档”），之后恢复正常。

## 原因

每次入账都要把整段聊天写一遍：酒馆没有只保存一条消息的接口，而防止重复入账的来源标记就存在那条回复上。旧版保存后还要把整个聊天文件读回来，只为核对这一个标记。酒馆自己在每条回复后也会整段保存一次，我们的保存排在它后面。楼层一高，一次入账要好几秒，原本很少撞上的事就会落进这段时间里：

1. **同一聊天的附加数据对象被替换**（TauriTavern 的 `updateChatMetadata`、其他扩展；9 月 #22 已确认用户环境里会发生）。10-12 的修复只在空闲时接上新对象，保存途中被换时：
   - 换在保存进行中：存档其实已经写进酒馆，但插件判定“聊天已变”，既没把这一版记为当前存档，也没解除待确认锁。面板看不到这条记录，提示“聊天已刷新”；下一条生成开始时抓不到起点，也没注入战阵上下文；回复扫描时重读存档，只能人工确认，就是那句提示。
   - 换在写恢复日志那一步：这条回复的改动被当成“聊天已切换”直接丢掉，还留下一条恢复记录。
2. **保存途中回复正文被改写**（rc.5 时已确认：宿主或其他扩展会在收到回复后再改一次正文）。旧版规定这种情况重扫后一律人工确认，哪怕 `<tb>` 一个字没变。
3. **原版 SillyTavern 跳过保存**：`saveChatConditional` 只等前一次保存 1 秒（`debounce_timeout.relaxed`），超时直接返回，不保存也不报错。带消息标记的保存读回仍是旧档时，旧版不重试，停在“还没确认保存成功”。
4. 面板把“保存还在进行”和“保存结束但没确认成功”显示成同一句红字。
5. 同样的严格比对还在两处：面板操作的回执（保存途中换了对象就报“聊天已切换，旧面板操作已停止”，其实已经保存）；发送战报（保存途中换了对象就只插入、不触发生成，提示“切聊天后未触发生成”）。

## 修改

- **保存流程容忍同一聊天的对象替换**（`NativeStore`）。写入、重试、撤销都改为判断“插件没重新读档、宿主仍在这个聊天”，不再要求宿主对象一模一样；磁盘读回照旧决定是否成功。
  - 存档写进保存那一刻宿主手里的对象。
  - 保存确认后，如果宿主换进来的对象里不是刚核实的这一版存档，就把这一版补进去，免得宿主下次保存把旧档写回去。
  - 读档时同样把磁盘上的存档补给缺失或过期的当前对象；有未确认的保存时不动。
- **读回仍是旧档时，整段补写一次**。原来只对不带消息标记的保存这样做，现在带标记的也算，覆盖 SillyTavern 跳过保存、保存途中被换对象两种情况。只在磁盘仍是保存前那一版时补写，不覆盖其他进度。
- **保存结束后的收尾**（`BattleService`）按“同一聊天、没重新读档”更新回执和状态，并接上新对象。命令版本记下读档次数；同一聊天换了对象，命令不再报“聊天或存档代次已变化”。
- **生成绑定跨重读保留**：回复扫描需要重读存档时，如果读到的仍是生成开始时那一份（文档和代次一致），就保留绑定。入账前照旧核对事实版本和单位版本；只有存档被整份替换才降为人工确认。
- **保存途中正文变化**：仍是同一条消息（角色、swipe、发送时间、完成状态一致），而且 `<tb>` 摘录完全相同，就继续自动入账。这与人工确认（`approve()`）判断来源是否变化的标准一致。事件、swipe 或消息本身变了，仍只出人工确认，旧值和新值都不自动执行。
- **跳过自动批准时写明原因**，例如“生成开始时上一次保存还没确认”“生成期间档案被替换”“保存途中回复里的事件被改动”“回复被编辑或切换过”“没有收到这次生成开始的事件”。以后再遇到，能直接看出卡在哪一步。
- **保存核验只读最新几条**。TauriTavern 上用聊天接口读文件头和最新一页：从带标记的消息到结尾，再多读 8 条余量，最多 200 条。以下情况仍整段读回：页里找不到、同一标记在聊天里出现两次、跨度超过 200 条，或者是原版 SillyTavern（读取接口只能整段返回）。发送战报后的确认也改为按页读。核对只需要带标记的那条消息，所以不跟副 API 的上下文层数挂钩。
- **面板状态**：保存进行中显示“保存中…”（不是红字，也没有“重新读取存档”按钮），回复的保存一开始就通知面板。保存结束仍没确认，才显示“上一次保存还没确认成功”。
- **面板回执和战报投递**改为只比对是否同一个聊天（新增 `sameChat`）；真的换了聊天仍然停止，战报也不在别的聊天里触发生成。

## 验证

- **新增测试**：
  - `runtime/tests/high-floor-auto-approve.test.ts`，10 项：保存中或写日志时被换对象、换入旧副本、生成途中换入不含存档的对象、存档被整份替换、只改正文与改动事件、生成开始时保存未确认、保存中的状态、宿主跳过保存。改动前的代码上全部失败。
  - `host/tests/native-host.test.ts` 新增 3 项：按页核验及几种退回整段读的情况；带标记的提交和战报确认不再读整段聊天；战报保存期间换了对象仍触发生成，换了聊天则不触发。
  - 这 13 项在改动前的代码上全部失败，改动后全部通过。
- **浏览器对照**：用本地合成宿主（`artifacts/high-floor/`，不入库）对比 test 渠道 `a5dc9b1` 的构建和改动后的构建。宿主模拟 TauriTavern：1200 楼（约 3 MB），保存串行，读写每 MB 约 0.7 秒；用户发言和每条回复后宿主各整段保存一次；另一个扩展在回复后 400 毫秒换入合并后的附加数据对象。每组连续生成三条带 `<tb>` 的回复。

  | 情形 | 改动前 | 改动后 |
  | --- | --- | --- |
  | 1200 楼，回复后换对象 | 甲、丙已写进酒馆，但面板看不到并锁住，提示“聊天已刷新”；乙整条丢失 | 三条都自动入账，每条约 5 秒 |
  | 20 楼，回复后换对象 | 三条都自动入账，每条约 0.2 秒（保存在替换前就结束） | 未测 |
  | 1200 楼，不换对象 | 每条约 7.3 秒入账 | 每条约 5.0 秒入账（省掉整段读回） |
  | 1200 楼，原版 SillyTavern（无按页接口），换对象 | 未测 | 三条都自动入账 |
  | 保存进行中打开面板 | 提示“上一次保存还没确认成功，请先处理上方提示”，不可操作 | 状态栏“保存中…” |

  页面控制台和服务端都没有错误。
- **按 test 渠道 CI 在本地重放**：`npm run typecheck` 通过。全量测试 2318 项，失败的只有基线里的 5 项 `unified-replay`，没有新增，也没有加载失败的测试文件。`test:extension`、`test:jev-relay`、MCP 测试、`build:extension` 加 `verify:dist` 都通过。`smoke:extension`（本机 Chrome）metadata-only 和 legacy-full 两种保存方式各 55 项全部通过。

## 限制和没做的

- 用的是合成宿主，没有连用户实际的 TauriTavern；耗时只反映上面的成本模型。
- 保存本身仍是整段写两次（宿主一次、插件一次），高楼层还是会慢几秒，只是不再出错。把插件的标记和存档并进宿主回复后的那次保存，可以再省一次整段写，但要改提交协议，这次没做。
