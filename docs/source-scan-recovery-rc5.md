# 0.2.0-rc.5：来源冲突恢复与战斗响应

用户反馈 rc.4 自动扫描后反复提示“来源消息已编辑、移动或删除”，放弃未落盘候选后手动扫描成功。复现发现：读取回复和写入来源标签之间存在异步存储窗口，正文可能在该窗口内完成最后一次更新；旧实现把标签写入前的来源冲突也保留为待核实保存，后续重试仍使用旧指纹。生成完成时间戳的更新也会误触发同一错误。

## 恢复行为

- 指纹仍严格检查正文、身份、消息位置对应内容、swipe、发送时间和完成状态，但不要求完成时间戳逐字相同。兼容 rc.1–4 保存的时间戳指纹。
- 来源标签批量校验全部完成后才写入。遇到来源冲突，独立读取宿主确认仍是前一存档后，才能移除未落盘候选和恢复记录。
- 自动扫描安全清理后最多重扫一次。新来源只产生人工确认候选，不能借重扫自动执行失效来源的事实变更。
- rc.4 遗留的此类待核实记录，升级后点击一次“核实并重试保存”即可核实、解锁和重扫。成功时返回新扫描自己的回执及操作身份，面板不再被旧错误覆盖。
- 候选已部分落盘、独立读回失败、恢复记录删除失败、聊天切换或宿主已有其他进度，仍保留待核实保护。不能把这些情形视作未保存并丢弃。

## 战斗响应

- 移动范围由每个格子单独寻路改为一次有预算限制的 Dijkstra。格子顺序、移动成本、路径平局规则、占位与飞行限制保持一致；AI 也使用同一入口。
- 一次同步点选与紧随其后的渲染复用动作预览。跨命令、异步保存或行动者切换不保留该查询结果。
- 战斗命令在计算前先绘制处理状态；命令仍串行，处理中重复点击不会重复执行。阵形草稿选中状态先显示，再等待保存核实。
- 没有跳过宿主保存或独立读回，也没有提前宣称保存成功。手机性能、聊天大小、服务器存储和网络时间仍影响最终耗时。

本地 Node 固定 `tacticalFixture`（5 单位、7×9 地图），每项 15 次的中位耗时如下。点选格 44 后立即渲染；新实现把点选返回的查询传给同一次渲染。这是 CPU 查询样本，不是实际手机或宿主的端到端测试。

| --- | ---: | ---: |
| 武器模式点选与渲染 | 1.785 ms | 0.802 ms |
| 移动模式点选与渲染 | 12.993 ms | 1.384 ms |
| 单独查询可达格 | 2.143 ms | 0.041 ms |

## 验证

- `npm run typecheck` 通过。
- `npm test`：100 个文件、760 项测试通过。新增来源变化恢复、真实编辑拒绝、部分落盘保护、异常与切聊天、人工候选事实保护、路径等价和预览复用回归。
- `npm run verify:compatibility` 通过，旧版本进度回退与恢复保持兼容。
- `npm run build:extension` 通过，版本与原生构建产物更新为 rc.5。
- Chromium 原生宿主夹具：`metadata-only`、`legacy-full` 两种模式各 41 项检查通过，无未处理页面异常。覆盖旧候选重载恢复、扫描竞态、慢保存期间反馈、重复点击只执行并保存一次，以及既有战报、触摸拖动和存档迁移行为。

上述浏览器验证使用合成宿主，尚未连接用户实际运行的 SillyTavern / TauriTavern 实例。
